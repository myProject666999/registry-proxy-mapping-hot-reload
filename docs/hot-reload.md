# 镜像代理规则与热加载设计

本文档规定 registry-proxy 的代理匹配规则、冲突裁决、改写语义以及规则热加载的
并发与可靠性行为。实现位于 `internal/rules`，集成见 `internal/config` 与
`internal/cmd`。

## 1. 规则模型

一条规则把一个**源前缀**映射到一个**代理目标前缀**：

```yaml
rules:
  - source: docker.io
    target: proxy-a.example
  - source: docker.io/library
    target: proxy-b.example/library
```

同时兼容旧的扁平 `proxies` 写法，等价于只有 host 段的规则：

```yaml
proxies:
  docker.io: docker.linkos.org
```

- 前缀由若干**路径段**组成，段之间用 `/` 分隔，第一段是 registry host（可带端口）。
- 前缀在比较前会做**规范化**：去除首尾空白、丢弃空段（连续/首尾斜杠无意义）、
  整体转小写。`Docker.IO/`、`docker.io`、`docker.io//` 规范化后完全相同。
- 每条规则保留其在源文件中的**位置（文件 + 行号）**，所有加载期错误都指向具体行。

## 2. 匹配裁决：最长前缀优先，按路径段计数

当多条规则同时能命中一个镜像时，**匹配段数最多的规则胜出**，与规则声明的先后
顺序无关。规则顺序永远不参与裁决。

以开头的两条规则为例：

| 镜像 | 命中的规则 | 结果 |
| --- | --- | --- |
| `docker.io/library/nginx:1.25` | `docker.io/library`（2 段，更长） | `proxy-b.example/library/nginx:1.25` |
| `docker.io/ketches/app:v1` | `docker.io`（1 段） | `proxy-a.example/ketches/app:v1` |

### 2.1 段边界

前缀只在**完整路径段**上匹配，不做字符串前缀匹配。`docker.io/lib` 不会命中
`docker.io/library/...`，因为 `lib` 与 `library` 是两个不同的段。这避免了
`lib` 意外匹配 `library`、`library-ish` 这类名字。

### 2.2 无法决出胜负的配置在加载期直接拒绝

最长前缀能裁决“包含关系”，但裁决不了“相同前缀”。以下情况在**加载阶段报错并拒绝
整份配置**，旧规则继续生效，运行时绝不随机挑选：

1. **同前缀冲突**：两条规则规范化后的前缀完全相同，但目标不同。错误信息同时给出
   两条规则的位置（文件:行号）和各自的目标。
2. **大小写/写法冲突**：仅大小写或斜杠写法不同、规范化后相同的前缀，视为同一前缀，
   目标不同即冲突。
3. 完全重复（前缀与目标规范化后都相同）是无害冗余，自动合并为一条，不报错。

## 3. 改写次数、改写链与环

**一次请求对一个镜像只改写一次，不做链式改写。**

- 每条规则的**目标前缀**都会进入一个“改写豁免集”（匹配结构里的 exempt 标记）。
  任何已经处于目标前缀下的引用，再次进入匹配时一律不再改写。因此把改写结果重新
  喂给引擎是幂等的：`rewrite(rewrite(x)) == rewrite(x)`。
- **改写环**（如 `a -> b`、`b -> a`，以及更长的环）意味着改写永远无法稳定，属于
  加载期硬错误，错误信息列出环上的所有规则及其位置。
- **非环改写链**：某条规则的目标恰好命中另一条规则的源（如 `docker.io -> mirror`
  且 `mirror -> upstream`）。由于只改写一次，第二条规则对从第一条进入的流量不会
  再生效；这种配置**允许加载但产生明确告警**，说明该规则在该路径上不会二次执行。
  直接引用 `mirror/...` 的请求同样因豁免而保持不变。

这样保证：无论配置如何组织，对已经改写过的结果重复处理，结果都不再变化。

## 4. 匹配结构与不可变快照

- 规则编译进一棵按段索引的内存 trie，规则终端节点持有规则，目标终端节点带豁免
  标记。最长前缀匹配就是沿输入段一路向下、记住最深的规则终端。
- 编译产物是一个 **`Snapshot`**：构建完成后不再修改，纯内存，**不含后台协程、文件
  句柄等需要显式释放的资源**。旧快照被处理较慢的请求持有时，由 Go GC 自然回收，
  因此不存在资源泄漏，也没有释放时机问题。
- 每个快照带单调递增的 **version** 和原始配置字节的 **SHA-256 checksum**。

## 5. 热加载

### 5.1 变更探测：监听父目录，而不是文件内容

规则文件在集群里通常以 ConfigMap 卷挂载。Kubernetes 更新 ConfigMap 卷时，是通过
**原子替换一组符号链接目录**完成的（`..data` 指向新的带时间戳目录，配置文件是经由
`..data` 的符号链接），而不是原地改写文件内容。

- 只监听文件内容会漏掉这种替换：路径背后的 inode 已经换了。
- 因此探测器 **fsnotify 监听配置文件所在的整个目录**。符号链接换入换出会在目录上
  产生 CREATE/REMOVE/RENAME 事件，原地写入会产生 WRITE 事件，两者都能覆盖。
- 监听目录会收到一串中间事件，这是可接受的：引擎对事件做**防抖合并**，并且每次都
  重新读取路径当前指向的内容，再用内容 checksum 去重。
- 探测器是一个接口（`Detector`）。生产用 fsnotify 实现；测试用 **`ManualDetector`**
  手动触发，完全不依赖真实文件系统事件，做到确定性。另有周期性 resync 作为丢失
  事件的兜底，内容未变时因 checksum 相同而近乎零成本。

### 5.2 加载流程：全部成功后再原子替换

一次加载严格按顺序执行：**读取 → 解析 → 校验 → 构建完整匹配结构 → 原子发布**。

- 只有所有步骤都成功，才用 `atomic.Pointer.Store` 替换当前快照。
- 任何一步失败，**旧快照原封不动继续生效**；失败通过日志和 Prometheus 指标暴露，
  日志带有出错规则的**位置和具体原因**，而不是一句笼统的“失败”。
- 构建新结构（规则量很大时本身耗时）在后台协程完成，**不占用请求路径上的任何锁**。

### 5.3 半写入防护：稳定读取（stable read）

文件可能在写到一半时被读到，且不完整内容恰好能解析。策略是**稳定双读**：连续两次
读取得到完全相同的字节，才认为写入完成、内容可信。

- 最坏情况：写入方持续不断地改文件，两次读取永远不一致。此时受 `stableTimeout`
  限制，超时后本次加载失败（`ErrUnstableRead`），旧规则继续生效，等下一次事件或
  resync 重试。不会发布任何中间态。
- 写入方在超时前结束：最终字节一旦落盘并稳定，下一次读取即得到最终内容。
- 读取函数可注入（`WithReadFunc`），测试用脚本化的字节序列确定性地复现
  “先抖动后稳定”，不依赖调度时序。

### 5.4 空文件视为错误

空文件（或解析后不含任何规则的文件）**拒绝加载**而不是解释为“没有规则”。这避免
一次误截断/误操作静默关闭全部改写。拒绝后旧快照继续生效。

### 5.5 快速连续变更的合并

发布流程几秒内连续改三次时，不需要每次都完整构建：

- 探测器通道容量为 1，事件在引擎繁忙时自然折叠；引擎侧再加防抖定时器，事件持续
  到来就不断顺延静默窗口，静默后**只对最新内容加载一次**。
- 硬性保证：**最终生效的一定是最后一次的内容**，任何中间版本都不会成为最终快照。
- 加载成功后日志记录规则**条数与内容摘要**（每条 `source -> target (位置)`）以及
  version、checksum，便于确认生效的正是自己提交的那一份。

## 6. 并发与请求内一致性

- 请求路径读取快照是**一次原子指针加载，无锁、无 I/O、无耗时操作**。
- 一个准入请求（一个 Pod 可能有很多容器、init 容器、临时容器）在**开始时取一次
  快照，全程复用同一个快照**。因此：
  - 单个请求从头到尾看到同一份规则，不会前半段旧规则、后半段新规则；
  - 切换完成后新到达的请求立即使用新规则。
- 切换仅替换指针；旧快照由 GC 回收。匹配结构纯内存、无后台资源，无需显式释放。

## 7. 可观测性指标

Prometheus 指标（命名空间 `registry_proxy`）：

| 指标 | 类型 | 含义 |
| --- | --- | --- |
| `rules_version` | Gauge | 当前生效快照的版本号 |
| `rules_loaded_total` | Gauge | 当前生效快照的规则条数 |
| `rules_active_checksum_info{checksum}` | Gauge(恒为1) | 当前生效快照内容的 checksum 标签 |
| `rules_reload_success_total` | Counter | 加载成功次数 |
| `rules_reload_failure_total{reason}` | Counter | 加载失败次数，按 `read/parse/empty/validate` 原因区分 |

通过 version 与 checksum 标签即可判断当前到底生效的是哪一份规则。

## 8. 测试覆盖

- `internal/rules/engine_build_test.go`（表驱动）：最长前缀、段边界、同前缀冲突、
  大小写冲突、目标命中其他规则（链告警/环拒绝/幂等）、legacy 格式、逐规则校验。
- `internal/rules/engine_test.go`：临时目录 + 手动探测器下的
  合法→非法→空文件→无规则文件→合法版本序列、失败保旧、稳定读取与超时、快速变更
  合并、symlink 原子替换探测、Prometheus 指标，以及 32 个协程持续匹配配合多次切换
  的竞态测试（`-race`），断言每个“请求”内结果始终来自同一版本。
- `internal/config`、`internal/cmd`：ConfigMap 驱动加载、失败保旧、默认值恢复，以及
  webhook 改写端到端与单次改写幂等。
